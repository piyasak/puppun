# Staging on Render + Supabase (G2-05, E-49)

PO decision (2026-10-09): host the staging service on **Render**, with the database and clip storage in the existing Supabase project **punpun**.

## What staging is

One Docker image (`Dockerfile`) runs the API and serves the built web app on the same origin. When it starts (`deploy/start.sh`), it runs `alembic upgrade head`, then uvicorn.

| Part | Where | Notes |
|---|---|---|
| API + web | Render web service `punpun-staging`, region Singapore (`render.yaml`) | Free plan sleeps when idle; the first request takes ~30 s. Starter (~$7/month) keeps it awake |
| Database | Supabase punpun Postgres, schema **`clipflow`** (`DB_SCHEMA`) | Never `public`: Supabase publishes `public` through its REST API to anyone holding the public key |
| Clip files | Supabase Storage, private bucket **`clipflow-media`** (created 2026-10-09), S3 protocol | **Free plan: 50 MB per file.** Clips of 3–5 min at 1080×1920 are often bigger, so uploads above the limit fail. Fix before the pilot: Supabase Pro, or another S3 store (e.g. Cloudflare R2) |
| Auth + email | Supabase Auth on punpun, Gmail SMTP, templates with `/auth/confirm` (E-28) | Site URL must be the staging URL, or email links point elsewhere |
| Rendering and posting | The customer's Agent | Nothing renders on the server; posting stays dry-run (not a setting) |

## One-time setup (PO; Claude cannot create accounts or enter secrets)

1. **Render:** sign in at render.com with GitHub. Allow access to `piyasak/puppun`.
2. **Render:** choose New → **Blueprint** → the repository. Render reads `render.yaml` and asks for every `sync: false` value:

   | Variable | Where to get it |
   |---|---|
   | `VITE_SUPABASE_PUBLISHABLE_KEY` | Supabase → Project Settings → API Keys → publishable key (public) |
   | `DATABASE_URL` | Supabase → **Connect** → **Session pooler** (port 5432). Paste the URI as shown and put the database password in it. `postgresql://…` is accepted |
   | `WEB_ORIGIN` | The service URL Render shows, e.g. `https://punpun-staging.onrender.com`. Fill it in after the first deploy if needed |
   | `OBJECT_STORAGE_ACCESS_KEY`, `OBJECT_STORAGE_SECRET_KEY` | Supabase → Storage → **S3 Connection** → New access key |

   `MEDIA_SIGNING_KEY` and `BILLING_SANDBOX_SECRET` are generated by Render. Secrets live only in Render, never in the repo, chat or logs.
3. **Supabase → Authentication → URL Configuration:**
   - Site URL = the staging URL.
   - Add `https://<staging-host>/**` to Redirect URLs.
   - Keep `http://localhost:3000/**` for local cloud tests.
4. **First deploy:** Render builds the image and starts it; the start step creates the `clipflow` schema and runs the migrations.
5. **Check it:**
   - `https://<staging-host>/healthz` returns `{"status":"ok","build":…}`.
   - The landing page opens.
   - Sign up with a real address and confirm through the email. This also proves E-28 against Microsoft 365 scanners, because the link is public now.
   - Then tell Claude, who checks:
     - the Supabase auth log;
     - that schema `clipflow` holds the tables and `public` stays empty;
     - that the role `anon` has no USAGE on `clipflow`.

## Every release

- **Automatic:** a push to `master` deploys only after GitHub CI is green (`autoDeployTrigger: checksPass`). CI includes the "Staging image build + smoke" job: build, start against Postgres, health and web/API checks, and `public` empty.
- **Migrations are expand-only between releases:** add tables and columns, never drop or rename in the same release. The previous image must still run on the new schema.
- **Verify:** `/healthz` shows the new `build`, plus one sign-in.

## Rollback

1. Render → the service → **Events** → choose the previous successful deploy → **Rollback**. This redeploys that image.
2. Because migrations are expand-only, the database needs no change. Check that `/healthz` shows the old `build`.
3. **A bad migration:** first deploy a release that fixes it forward. Use `alembic downgrade` only with the PO and a backup, because it can drop data. Downgrade inside the schema is tested (`services/api/tests/test_staging_image.py`).

## Rehearsal on the QA PC

```bash
.venv/Scripts/python tools/staging_rehearsal.py
```

The script builds v1 and v2 of the real image, then deploys v1, releases v2 and rolls back to v1 against a throwaway database with `DB_SCHEMA=clipflow`. Every step checks the build ID, the web app, the API and an empty `public`. The result goes to `var/evidence/staging_rehearsal.json`, which is not committed.

The 2026-10-09 run was healthy in 4.3 s, 2.8 s and 2.8 s, with 23 tables in `clipflow` and 0 in `public`.
